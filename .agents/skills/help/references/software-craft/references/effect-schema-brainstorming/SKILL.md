# Effect Schema Brainstorming

Make production schemas, generated examples, and functional properties the shared language of the conversation. Iterate on the schemas that the final implementation imports; never create disposable copies merely for brainstorming.

## Inputs

- The domain idea, requirements, and decisions already made
- The owning Effect workspace and current production schemas when present
- Existing public behavior and focused tests when present

Use this skill for domain discovery that directly shapes the production schema.

## Ground the workspace

1. Read the shared [Effect context](../effect.md), then locate the workspace package that owns the domain and declares Effect v4. Read the installed Effect package's `AGENTS.md` and relevant source.
2. Locate the existing production schema module, its exports, callsites, and tests. Edit those schemas in place. For a new domain, create the schema in its intended final source module following package conventions.
3. Never place production schemas, competing copies, or wrapper schemas in a scratch directory. Keep test-only scenario schemas in the package's normal test location unless they are real domain concepts that belong in production.
4. Give every named production schema, type alias, interface, class, and named nested data structure its own JSDoc comment that states its domain role and includes a realistic `@example` usage. Document exported decoded types separately from their schema values. Name meaningful nested structures instead of hiding them in anonymous `Schema.Struct` declarations; inline primitive composition does not need JSDoc.
5. Generate examples directly from the production schema symbols. Keep permanent tests in the package's normal test location. Use a one-off runner for sample printing unless the package already has a samples convention, then delete that runner after capturing its output.

Keep one production working set throughout the conversation. Every accepted answer updates the same schema symbols that the final implementation uses.

## Run the brainstorming loop

1. Translate the current idea into the canonical production schema symbols. Iterate sequentially on those symbols; preserve earlier examples and tradeoffs in the conversation, not as parallel schema declarations. Define multiple schemas only when each represents a distinct production-used domain concept.
2. Encode agreed constraints in the production schemas. Keep disputed rules visible as named requirements until the user chooses them. Distinguish parsing from validation: do not add restrictions when the domain only needs structural parsing. Whenever shape or meaning changes, update the JSDoc and `@example` on every affected schema, type alias, interface, class, named nested structure, and exported decoded type; stale examples are defects.
3. Derive generators from the canonical production symbols with `Schema.toArbitrary(schema)(FastCheck)`. Do not maintain hand-written generators or parallel brainstorming schemas. When a property needs generated setup that is not a domain concept, define that test-only scenario beside the test.
4. Generate a small, varied sample for the current production schema with `FastCheck.sample`. Run sampling separately from the test suite: examples support the conversation but assert no behavior. Use `andrue-cli generate` only when the production module already follows its required export convention; do not reshape production exports for the tool.
5. Turn each property into an executable requirement:
   - name the test after an actor-visible outcome;
   - generate the story's inputs or starting state from the production schemas;
   - exercise the public operation, command, or workflow that owns the behavior;
   - assert its observable output and state changes;
   - derive the oracle from the requirement, not the implementation or schema mechanism;
   - test encode/decode round trips only when a transformation is part of the user-facing contract.
6. Reject self-validating checks. Schema conformance generated by the same schema supplies no evidence and must not appear as a property. This excludes:
   - decoding a value generated from the same schema;
   - checking a generated field against the check that generated it;
   - checking that a tagged payload belongs to the union used to construct it;
   - checking that an output parses without a stated behavioral consequence.
7. Identify the public contract from package exports, a CLI executable, an HTTP handler, or the application workflow named by the user. Exercise that boundary. For CLI work, inspect stdout, exit status, and filesystem effects. Call a source helper only when it is the requested surface.
8. When public behavior does not exist yet, still place the schema in its final production module. Use generated examples to agree on the contract, record named future behavioral requirements, and hand the selected schema to implementation planning without fabricating behavior or tests.
9. When an implemented public contract exists, run its focused functional properties after every schema revision. Treat a shrunk counterexample as a design example to discuss, not noise to suppress.
10. Present production schema paths, exact definitions, representative generated values, and any requirement or story results. Compare the previous iteration from conversation history. Ask one concrete domain question exposed by the current examples.
11. Apply each answer directly to the canonical production schemas and affected callsites. Remove superseded schema structure, stale properties, and one-off sample runners. Regenerate examples and rerun focused tests when they exist before the next question.

Before retaining a property, name one plausible public-behavior defect it would catch. Delete any property that could pass with that defect present.

## Minimal pattern

```ts
// src/Cart.ts
import { Schema } from "effect"

/**
 * A priced item included in a cart.
 *
 * @example
 * const item = CartItem.make({ price: 25, quantity: 2 })
 */
export const CartItem = Schema.Struct({
  price: Schema.Int.check(Schema.isBetween({ minimum: 1, maximum: 100 })),
  quantity: Schema.Int.check(Schema.isBetween({ minimum: 1, maximum: 10 }))
})

/**
 * A decoded item consumed by cart operations.
 *
 * @example
 * const item: CartItem = CartItem.make({ price: 25, quantity: 2 })
 */
export type CartItem = typeof CartItem.Type

/**
 * A cart submitted for pricing.
 *
 * @example
 * const cart = Cart.make({ items: [CartItem.make({ price: 25, quantity: 2 })] })
 */
export const Cart = Schema.Struct({
  items: Schema.Array(CartItem)
})

/**
 * Decoded cart data accepted by `quote`.
 *
 * @example
 * const cart: Cart = Cart.make({ items: [] })
 */
export type Cart = typeof Cart.Type
```

Generate discussion examples directly from that production export:

```ts
import { Schema } from "effect"
import { FastCheck } from "effect/testing"
import { Cart } from "./src/Cart.ts"

console.log(FastCheck.sample(Schema.toArbitrary(Cart)(FastCheck), 5))
```

Keep functional properties in the normal test suite:

```ts
// test/Cart.test.ts
import { test } from "bun:test"
import { Schema } from "effect"
import { FastCheck } from "effect/testing"
import { Cart, quote } from "../src/index.ts"

const carts = Schema.toArbitrary(Cart)(FastCheck)

test("a quote totals every item in the cart", () => {
  FastCheck.assert(
    FastCheck.property(carts, (cart) => {
      const expected = cart.items.reduce(
        (total, item) => total + item.price * item.quantity,
        0
      )
      return quote(cart).total === expected
    }),
    { numRuns: 100 }
  )
})
```

Use the repository's existing test runner around the same `FastCheck.property` body when it is not Bun.

## Output

For each iteration, return:

1. **Schemas** — production file path and current exact definitions.
2. **Examples** — a compact set from the current production schema, with the previous iteration's relevant difference.
3. **Properties** — requirement or story names and pass/fail results when implemented behavior exists.
4. **Question** — one domain decision that changes the canonical production schemas or properties.

## Done

The user has selected the model; the production schemas and affected callsites reflect it; every named production schema, type alias, interface, class, named nested structure, and exported decoded type has current domain-role JSDoc and a realistic `@example`; and direct-import sampling produces the final examples. When public behavior exists, the agreed behavior-linked properties pass. No temporary candidate or sample artifact remains.
